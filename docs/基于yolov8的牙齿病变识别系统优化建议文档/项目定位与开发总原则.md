# 项目定位与开发总原则

## 一、项目定位

当前项目应定位为：

> 基于已训练 YOLO 牙齿病变检测模型的前台识别系统。

也就是说，用户拿到的是一个已经训练完成、已经可以用于推理的模型。用户不需要关心训练过程，也不需要具备训练服务器、训练数据集、YOLOv8 源码修改能力。用户只负责使用前台系统完成上传、检测、查看、保存、导出、辅助理解等操作。

本项目不应被设计成训练平台、标注平台、主动学习平台、医院级系统平台，也不应让普通用户承担模型迭代任务。

合理的用户流程是：

1. 启动本地项目。
2. 进入前台识别界面。
3. 选择默认模型或在设置中切换已存在模型。
4. 上传单张或多张牙科影像。
5. 点击开始分析或批量分析。
6. 查看原图、模型输入图、检测结果图、检测框表格、图像质量提示、辅助建议。
7. 根据需要导出报告、保存病例记录、导出批量结果。
8. 可选地使用 AI 问答功能继续理解检测结果。

## 二、当前项目已有能力

当前项目已经具备较完整的前台识别基础，不需要推翻重做。后续优化应该基于现有功能做增量增强。

已有能力包括：

1. Gradio 前端工作台。
2. 单张图片上传与检测。
3. 批量图片上传与逐张查看。
4. 原图、模型输入图、检测结果图三图展示。
5. 检测框表格展示。
6. 可选 CLAHE 增强。
7. 图像质量提示。
8. 模型目录扫描。
9. 主模型路径和对比模型路径配置。
10. 单模型与对比模型模式。
11. 单图报告压缩包导出。
12. 批量结果压缩包导出。
13. 病例记录保存与查看。
14. AI 建议与 AI 问答。
15. OpenAI 兼容接口配置。
16. 配置持久化和存储目录配置。
17. API Key 安全保存选项。

后续开发的重点不是新增训练能力，而是提升前台识别系统的可用性、可读性、可导出性和结果管理能力。

## 三、明确不做的内容

### 1. 不做模型复训练

不要在前台中加入以下功能：

- 重新训练模型。
- 继续训练模型。
- 一键训练模型。
- 根据用户反馈自动训练。
- 导出样本后自动上传服务器训练。
- 定期复训练。

原因是普通用户没有训练代码、训练数据、服务器资源，也不应被要求理解训练流程。引入复训练功能会让项目定位变得混乱，而且会显著增加工程复杂度。

### 2. 不做主动学习

不要实现主动学习功能，例如：

- 自动挑选难例。
- 自动生成待标注数据集。
- 用户确认后加入训练集。
- 定期根据用户反馈更新模型。

这些功能属于训练闭环或数据闭环，不属于当前前台识别系统的合理范围。

### 3. 不做在线标注平台

不要把本项目改造成 Label Studio、Roboflow、CVAT 这类在线标注系统。可以保留简单的病例备注、结果备注，但不要加入复杂的画框、编辑框、标签导出、标注任务分配等功能。

### 4. 不做医院级系统集成

当前阶段不要做：

- PACS 深度集成。
- DICOMweb。
- 医院信息系统对接。
- 保险理赔。
- 收费系统。
- 多用户权限。
- 审计日志。
- 医疗器械合规流程。

这些功能工程量很大，而且会偏离“基于已训练模型的牙齿病变前台识别系统”这一核心目标。

## 四、后续优化总方向

后续优化应该围绕四条主线展开。

### 方向一：让用户更容易理解检测结果

包括：

- 置信度等级解释。
- 类别中文名称。
- 检测结果图例。
- AI 建议结构化。
- 图像质量提示增强。
- 安全声明明确化。

### 方向二：让结果查看更方便

包括：

- 检测结果图放大查看。
- 检测结果图下载。
- 疑似区域局部裁剪。
- 批量检测结果总览。
- 重点关注图片列表。

### 方向三：让记录管理更完整

包括：

- 病例搜索。
- 病例筛选。
- 病例删除或移入回收站。
- 病例导出。
- 检测历史记录。
- 报告与病例记录关联。

### 方向四：让报告导出更正式

包括：

- Word 报告。
- PDF 报告。
- 批量汇总报告。
- 报告模板美化。
- 报告中包含检测图、检测表、质量提示、辅助建议、安全声明和模型说明。

## 五、代码开发总原则

### 1. 不建议继续把所有逻辑堆进 app.py

当前 app.py 已经承担了大量布局、事件绑定和业务逻辑。后续新增功能时，应尽量把业务逻辑拆分到 src/dental_detection 目录下的新模块中。

建议新增模块：

```text
src/dental_detection/reporting.py
src/dental_detection/batch_summary.py
src/dental_detection/result_levels.py
src/dental_detection/image_quality.py
src/dental_detection/case_store.py
src/dental_detection/history_store.py
src/dental_detection/model_info.py
src/dental_detection/visualization.py
```

app.py 应主要负责：

1. Gradio 组件布局。
2. 用户事件绑定。
3. 调用业务模块。
4. 更新界面输出。

业务模块应负责：

1. 报告生成。
2. 批量统计。
3. 置信度等级计算。
4. 图像质量分析。
5. 病例记录管理。
6. 历史记录管理。
7. 模型信息整理。
8. 结果图保存和局部裁剪。

### 2. 不破坏现有功能

新增功能必须保证旧功能仍然可用，包括：

- 单图检测。
- 批量检测。
- CLAHE。
- 模型切换。
- AI 建议。
- AI 问答。
- 报告压缩包导出。
- 批量压缩包导出。
- 病例记录保存。
- 设置保存。

### 3. 优先本地可运行

不要引入必须联网、必须云服务、必须数据库服务、必须 Docker、必须 Redis 的功能。

建议优先使用：

- Python 标准库。
- 当前已有依赖。
- 轻量新增依赖。

如果新增依赖，必须写入 requirements.txt，并说明用途。

### 4. 中文兼容优先

所有面向用户的提示、报告、文件名、按钮、表格列名应优先使用中文。

导出 Word 或 PDF 时要重点考虑中文显示问题。第一阶段建议优先实现 Word 报告，因为 Word 对中文更友好，用户也方便二次编辑。

### 5. 安全声明必须保留

所有报告、建议、AI 回复、病例记录中都必须保留类似声明：

> 本结果仅供辅助参考，不能替代专业牙科医生诊断。

不要出现以下表达：

- 确诊。
- 一定是。
- 必须治疗。
- 处方。
- 药物剂量。
- 自行用药建议。

### 6. 不上传牙片给 AI

当前项目设计中，AI 只接收检测结果文本，不接收牙片图片。这是合理的隐私边界。后续不要擅自把原始牙片或结果图上传给外部大模型。

## 六、推荐开发顺序

建议按以下顺序开发：

1. 第一档：正式报告导出、批量检测总览、置信度等级解释、结果图查看增强、病例管理增强、图像质量增强。
2. 第二档：模型信息说明、模型卡片式选择、检测历史、批量合并报告、AI 建议结构化、类别图例。
3. 第三档：演示样例库、牙位粗定位、检测框显示开关、结果图下载、新手引导、异常提示优化。
4. 第四档：明确暂不实现或仅作为远期设想的功能，避免项目跑偏。
